# Queue Build Process

Like many modern webapps, the Queue utilizes a build system to transform and bundle source code into assets that are served to the client. We use [Next.js](https://nextjs.org/) as the basis of the frontend tooling. Next.js takes care of client-side routing, splitting code across routes, transpiling JSX and TypeScript, and more.

In April 2019, the Queue began adopting [TypeScript](https://www.typescriptlang.org/) for both client-side and server-side code. Because TypeScript is used on the server as well, we introduced a compilation step for the server code. Although Next.js supports custom servers, it does not transpile non-page server code, so we have a custom build process. You can see the full command for this in `package.json` under the `build` script. The general process is explained below.

First, we run the standard Next.js build process with `next build`, which outputs compiled assets (scripts, stylesheets, etc.) into the `.next` directory. Next, we invoke the TypeScript compiler (`tsc`) on the `src` directory to compile all of the server files into JavaScript files in a `build` directory. Note that although some shared modules and React components are also compiled in this phase, only the bundled assets generated by the Next.js toolchain are actually served to the client in production. Finally, we manually copy the static files from `src/static` to `build/static`, as the `tsc` compiler does not copy these files.

In development (`npm run dev`), we use [`ts-node`](https://github.com/TypeStrong/ts-node) to compile and execute TypeScript on the fly. You can also use [nodemon](https://nodemon.io/) via `npm run dev-watch`, which restarts the server when files change. This is mostly useful when working on the server side, as Next.js automatically hot-reloads client code in development mode.
